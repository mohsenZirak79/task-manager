# Reports backend update v1.2.0

این ZIP بسته به‌روزرسانی بک‌اند موجود است، نه نصب مستقل. فایل‌ها از ریشه Laravel آغاز می‌شوند.
پایه موردنیاز: بک‌اند v1.4.2 یا نسخه main متناظر، PHP 8.3+ و وابستگی‌های نصب‌شده.
فایل‌های لازم گزارش مصوبات، workflow، پیوست، دیدگاه و گزارش مستقل در این بسته هستند.
وابستگی Composer جدیدی اضافه نشده است. هیچ تغییری برای فرانت‌اند در بسته وجود ندارد.

## انتشار روی سایت فعال

1. از کد و دیتابیس سرور نسخه پشتیبان بگیرید. ZIP را ابتدا در پوشه موقت باز کنید.
2. فقط فایل‌های فهرست REPORTS_INCLUDED_FILES.txt را در همان مسیرهای ریشه بک‌اند (کنار artisan) جایگزین کنید.
   پوشه پروژه یا پوشه‌های app/database/routes را پاک نکنید؛ فایل‌های ZIP را روی آن‌ها کپی کنید.
3. برای جلوگیری از درخواست به کد جدید قبل از آماده شدن دیتابیس، در پنجره کوتاه انتشار اجرا کنید:

```bash
php artisan down
```

4. بعد از جایگزینی فایل‌ها، از ریشه همان بک‌اند اجرا کنید:

```bash
php artisan optimize:clear
composer dump-autoload --optimize --no-scripts
php artisan migrate --force
php artisan access:sync
php artisan optimize
php artisan up
```

اگر فرمانی خطا داد، پیش از بالا آوردن سایت علت را رفع کنید؛ راهنمای rollback پایین را ببینید.
پردازش‌های ماندگار مثل queue worker و Octane، اگر استفاده می‌شوند، طبق روال سرور بازراه‌اندازی شوند.

## حفظ تنظیمات و داده‌های سایت

ZIP شامل هیچ .env یا .env.example، config، bootstrap، vendor، composer.json/lock، storage، public،
فایل دیتابیس، آپلود، لاگ، .git یا کش محیط توسعه نیست. با کپی فقط فایل‌های بسته، این موارد بازنویسی نمی‌شوند.
APP_KEY، تنظیمات اتصال دیتابیس، دامنه، ایمیل و مسیر storage همان مقادیر فعلی سرور باقی می‌مانند.
composer install/update/setup، key:generate، migrate:fresh، migrate:refresh و db:seed اجرا نکنید.
این انتشار دیتابیس را با migration تغییر می‌دهد؛ قرار نیست داده یا ساختار دیتابیس بدون تغییر بماند.

## تغییرات دیتابیس و مجوزها

- migration گزارش مصوبات در صورت اجرا نشدن قبلی اجرا می‌شود.
- migration workflow به گزارش‌های موجود شماره RPT می‌دهد، status=sent و sent_at=created_at قرار می‌دهد؛
  پشتیبانی پیوست و دیدگاه گزارش را اضافه می‌کند. اگر قبلاً اجرا شده باشد دوباره اجرا نمی‌شود.
- migration جدید meeting_resolution_id را nullable می‌کند؛ ارتباط و محدودیت یکتایی مصوبات قبلی حفظ می‌شود.
- access:sync نقش‌های داخلی را با تعریف پروژه همگام می‌کند؛ reports:manage به نقش User اضافه می‌شود.
  این فرمان مجوزهای سفارشیِ اضافه‌شده به نقش‌های داخلی را مطابق تعریف رسمی همگام می‌کند؛
  قبل از اجرا، مجوزهای سفارشی نقش‌های داخلی را بررسی کنید. نقش‌های سفارشی مستقل حفظ می‌شوند.
- گزارش مستقل را سازنده یا مدیر می‌تواند مدیریت کند؛ گیرنده و رونوشت حق مشاهده و دیدگاه دارند.

## بررسی پس از انتشار و rollback

ورود و APIهای موجود، ثبت مستقل با POST /api/v1/reports، ارسال پیش‌نویس و مشاهده توسط گیرنده را بررسی کنید.
گزارش مستقل باید meeting_resolution_id، meeting و resolution برابر null داشته باشد.
گزارش‌های مصوبه قبلی باید همچنان قابل دریافت باشند.
تست‌های مرتبط روی SQLite موقت پاس شده‌اند؛ دیتابیس سرور از این محیط اجرا یا آزمایش نشده است.
برای rollback کد و دیتابیس را از نسخه پشتیبان همان انتشار هماهنگ بازگردانید.
rollback migration workflow دیدگاه‌های گزارش را حذف می‌کند؛ آن را به عنوان rollback بی‌خطر اجرا نکنید.
rollback nullable-resolution در صورت وجود گزارش مستقل عمداً متوقف می‌شود تا داده از دست نرود.
