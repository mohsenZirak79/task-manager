# تکمیل تسک‌های ذیل گزارش — ۲۰۲۶/۱۱/۱۶

این تغییرات محلی‌اند و هنوز منتشر نشده‌اند. رابطه، API ثبت تسک و نمایش گزارش مبدأ از قبل وجود داشتند؛ این اصلاح مسیر استفاده و توضیح مجوزها را تکمیل می‌کند. migration جدید لازم نیست.

## گردش کار

۱. گزارش مستقل یا مرتبط با مصوبه از مسیر موجود ثبت و ارسال می‌شود.
۲. مخاطب اصلی، گزارش را مشاهده می‌کند. پس از ثبت مشاهده، `allowed_actions.create_task` برای مخاطبی که مجوز ایجاد تسک دارد فعال می‌شود.
۳. در جزئیات گزارش، علاوه بر دکمه قبلی بالای صفحه، «ثبت تسک ذیل گزارش» کنار فهرست تسک‌های مرتبط قرار دارد. فرم کامل موجود، اطلاعات پیشنهادی گزارش را دریافت می‌کند و عنوان و جزئیات قابل ویرایش‌اند.
۴. ثبت موفق، یک تسک واقعی با `source_report_id` متصل به همان گزارش ایجاد می‌کند. چند تسک برای یک گزارش مجاز است؛ تکرار همان درخواست تسک جدید نمی‌سازد.
۵. تسک‌های قابل مشاهده و صفحه‌بندی آن‌ها زیر گزارش نمایش داده می‌شوند. در جزئیات تسک، «گزارش منبع» و لینک بازگشت طبق مجوز موجود نمایش داده می‌شود.

طبق تأیید کاربر، فقط مخاطب اصلی گزارشِ مشاهده‌شده می‌تواند تسک ثبت کند. ثبت‌کننده، رونوشت و مدیر غیرمخاطب استثنا ندارند. API همان Policy را هم در FormRequest و هم زیر قفل تراکنش بررسی می‌کند. بخش فهرست در نبود مجوز مشاهدهٔ ماژول تسک، درخواست غیرمجاز نمی‌فرستد و پیام دسترسی نمایش می‌دهد.

## قرارداد API

- `POST /api/v1/reports/{report}/create-task`: همان ورودی ایجاد تسک، همراه `submission_type` و `submission_key` از نوع UUID؛ 201 برای ایجاد و 200 با `replayed:true` برای تکرار همان درخواست. یک UUID با payload متفاوت 409 می‌دهد.
- `GET /api/v1/reports/{report}/tasks?page=1&per_page=15`: تسک‌های مجاز همان گزارش با `data.items/meta`.
- `GET /api/v1/reports/{report}`: شمارش تسک‌های مجاز، `tasks_url`، پیشنهادهای فرم و دسترسی ایجاد.
- `GET /api/v1/tasks/{task}`: `report_source:{id,title}` فقط وقتی گزارش برای همان کاربر قابل مشاهده است؛ برای تسک نامرتبط یا گزارش غیرمجاز null.

افزودهٔ سازگار به تمام خروجی‌های ReportResource:

```json
{
  "allowed_actions": { "create_task": false },
  "task_creation": {
    "allowed": false,
    "reason": "report_not_viewed",
    "message": "پس از ثبت مشاهدهٔ گزارش توسط مخاطب، ایجاد تسک فعال می‌شود."
  }
}
```

این نمونه قراردادی است. هنگام مجازبودن، `allowed:true` و reason/message برابر null هستند. مجوز اصلی همچنان `allowed_actions.create_task === true` است؛ فیلد کمکی اجازهٔ مستقلی ایجاد نمی‌کند. علت‌ها: inactive_user، not_report_recipient، report_not_sent، report_not_viewed، report_inactive، report_not_visible، task_creation_not_allowed.

رابطهٔ دیتابیس، جلوگیری از حذف گزارش مرجع، ممنوعیت جعل/تغییر منبع، سیاست مشاهدهٔ تسک‌ها و قرارداد قبلی درخواست‌ها حفظ شده‌اند. فیلد جدید nullable مستقل برای ارتباط ساخته نشده و ارتباط تکراری وجود ندارد.

[قرارداد کامل OpenAPI](task-manager-frontend-api-taskover.json) همچنان شامل ۷۱ مسیر و ۹۴ عملیات است؛ فیلد پاسخ جدید به آن اضافه شده است.

## آزمون واقعی

- SQLite مرتبط: ۹۹ تست، ۹۷ موفق، ۲ skip مختص snapshot داشبورد MySQL، ۱۲۵۵ assertion.
- MySQL 8.4 مستقل: ۲۱ تست ReportTaskTest، همگی موفق، ۱۷۴ assertion.
- فرانت مرتبط: ۳۸ تست، همگی موفق؛ شامل رندر فهرست و دکمه، علت غیرفعال‌بودن، جلوگیری از درخواست فهرست بدون مجوز، کلید ثبت و لینک دوطرفه.
- build بهینه Next.js با ۲۴ صفحه static و lint فایل‌های مرتبط موفق‌اند.

تست گردش کامل با API واقعی در دیتابیس تست انجام شد؛ در production رکورد آزمایشی ساخته نشد. دو تست snapshot داشبورد که در SQLite skip شدند جزو اجرای MySQL این اصلاح نبودند. آخرین تلاش اتصال سرور با Connection refused مواجه بود؛ انتشار این اصلاح تأیید یا انجام نشده است.

فایل‌های اصلی این اصلاح: ReportPolicy، ReportResource، ReportTaskTest، ReportRelatedTasks، ReportDetailPage، reportTaskUi.test.mjs و قرارداد کامل API. تغییرات محلی نامرتبط مدیریت کاربران و تنظیم تست در این اصلاح وارد نشده‌اند.
