# Workflow fixes — 2026-10-13

- Approved request assignees may edit planning with `PATCH /tasks/{id}/planning`
  and record weighted progress with `PATCH /tasks/{id}/planning-items/{itemId}`.
  Both require the selected assignee and a ready-to-start/in-progress task.
- Both upload endpoints accept `files[]` (1–20 files), returning `data.files`.
  Existing single `file` requests keep returning `data.file`. All files are
  validated before storage. Public media URLs use `/storage/...`; clients must
  resolve them against the API origin. The public storage symlink is required.
- Report creation accepts an optional `submission_key` (16–100 characters).
  The frontend keeps this key for retries and generates a new one for a new
  report. A transactional creator lock and database unique constraint prevent
  duplicate standalone reports; resolution reports reuse a matching key too.
- `POST /meetings/{id}/start` is available to the creator or secretary of a
  scheduled, unstarted meeting. It records `started_at` and locks meeting edits.
- `POST /meetings/{id}/view` records an acknowledgement by other meeting members
  before explicit start. Repeated acknowledgement is harmless. Meeting details
  return `viewed_at` for the current user and `allowed_actions.start`,
  `allowed_actions.acknowledge`, and `allowed_actions.edit`.
- Run migrations before serving the updated backend. The frontend hides the
  generic change-status button on task detail pages and exposes planning
  management on both detail and planning-only edit pages.
