# امضای مصوبات نهایی جلسه

وضعیت: کد 6a3836b89b34eeb5f9531e78645d7b614057bc48 روی main پوش و روی https://taskover.ir منتشر شده است. migration اجرا شده و فایل‌های فرانت تغییر نکرده‌اند.

## قاعدهٔ تأییدشده

امضا فقط پس از `status=completed` مجاز است و تأیید متن نهایی مصوبات توسط کاربر واردشده محسوب می‌شود. امضای مبتنی بر گواهی دیجیتال یا درج تصویر امضای پروفایل نیست.

- فقط کاربر فعال با مجوز موجود `meetings:view` و عضویت واقعی در `meeting_attendees` می‌تواند از طرف خودش امضا کند. مدیر و سوپرادمین هم باید شخصاً عضو باشند. رئیس و دبیر طبق منطق قبلی پروژه به حاضرین اضافه می‌شوند.
- مشاهده، شروع، ارسال و اتمام جلسه مستقل می‌مانند. مشاهده به معنای امضا نیست؛ امضا مشاهده یا اتمام را ثبت نمی‌کند؛ اتمام نیز منتظر امضای همه نمی‌ماند.
- وضعیت جدیدی به enum جلسه اضافه نشده است. قفل‌های فعلی ویرایش جلسه/مصوبات پس از اتمام حفظ می‌شوند. هیچ مسیر بازگشایی یا ویرایش جلسهٔ نهایی اضافه نشده است.
- درخواست تکراری برای همان کاربر/جلسه/محتوا موفق است و زمان اولین امضا حفظ می‌شود. زمان از ساعت سرور گرفته می‌شود.

## قرارداد API

ابتدا `GET /api/v1/meetings/{meeting}` را دریافت کنید. پاسخ کامل قبلی حفظ شده و این موارد به آن اضافه شده‌اند:

- `data.meeting.signature_content_version`: شناسهٔ محتوایی ۶۴کاراکتری همان متن نمایش‌داده‌شده.
- `data.meeting.allowed_actions.sign`: امکان نمایش دکمهٔ امضای کاربر جاری، فقط برای محتوای هنوز امضانشده.
- هر عضو در `data.meeting.attendees` تمام فیلدهای قبلی UserSummary را دارد، به‌علاوه:

| فیلد | معنا |
|---|---|
| `signature_status` | `unsigned` امضانشده، `signed` امضای همین محتوا، `outdated` امضای محتوای قبلی |
| `signed_at` | زمان ISO 8601 امضای **محتوای فعلی**؛ برای unsigned/outdated برابر null |
| `signed_content_version` | شناسهٔ محتوایی که این فرد امضا کرده؛ برای unsigned برابر null و برای outdated مربوط به نسخهٔ قبلی |
| `can_sign` | فقط برای ردیف خود کاربر و در صورت احراز شرایط true است |

اسامی کامل در `full_name` و شناسه‌ها در `id` از قبل وجود دارند. فهرست خلاصهٔ جلسات تغییری ندارد. خروجی عملیات قبلی که MeetingResource برمی‌گردانند نیز همین فیلدهای افزایشی را دارند.

```http
POST /api/v1/meetings/{meeting}/sign
Authorization: Bearer <TOKEN>
Accept: application/json
Content-Type: application/json
```

```json
{
  "content_version": "<مقدار signature_content_version دریافتی از GET>"
}
```

مقدار بالا باید از پاسخ واقعی خوانده شود؛ متن داخل <> و هش‌های نمونه را ثابت ارسال نکنید. فیلدهای `user_id`، `attendee_user_id`، `signed_at`، `signature_file_id` و `content_snapshot` برای ارسال توسط کلاینت ممنوع‌اند. هویت امضاکننده از احراز هویت گرفته می‌شود.

پاسخ ۲۰۰ همان envelope فعلی است: `success/message/data.meeting` با وضعیت به‌روز امضاها. تکرار امضای ثبت‌شده نیز ۲۰۰ است، حتی اگر UI اکنون `can_sign=false` نمایش دهد.

| کد | رفتار |
|---|---|
| 401 | ورود لازم است |
| 403 | نبود مجوز/عضویت، حساب غیرفعال یا جلسه‌ای که completed نیست |
| 404 | جلسه یافت نشد یا حذف شده است |
| 409 | محتوای فعلی با نسخهٔ مشاهده‌شده متفاوت است؛ GET مجدد، نمایش متن جدید و گرفتن تأیید مجدد کاربر |
| 422 | نسخهٔ ناقص/نامعتبر یا ارسال هویت، زمان و سایر فیلدهای ممنوع |

## نمایش مطابق طرح

- `signed`: تیک آبی و زمان `signed_at` نمایش داده شود.
- `unsigned`: برای وضعیت و زمان «ـ» نمایش داده شود.
- `outdated`: نیاز به امضای مجدد مشخص شود؛ زمان امضای قدیمی به‌عنوان امضای متن فعلی نمایش داده نشود.
- دکمه فقط برای ردیفی با `can_sign=true` فعال باشد و هنگام درخواست غیرفعال شود. بعد از موفقیت، دادهٔ جلسه از پاسخ جایگزین یا query آن invalidate شود.
- تاریخ نمونهٔ طرح را از ISO سرور به تاریخ شمسی و ساعت `Asia/Tehran` تبدیل کنید. سرور تاریخ شمسی یا تصویر تیک تولید نمی‌کند.

## نسخه و حفظ سابقه

نسخه، SHA-256 از JSON محتوای مصوبات با ترتیب ثابت کلیدهای object است؛ ترتیب آرایه‌ها حفظ می‌شود. شمارهٔ ترتیبی ویرایش نیست: محتوای کاملاً یکسان همان شناسه را دارد. این شناسه برای تطبیق متن است، نه امضای رمزنگاری‌شدهٔ شخص.

اطلاعات مشمول نسخه: عنوان/خلاصه/مکان/تاریخ/ساعت جلسه، شناسهٔ رئیس و دبیر و حاضرین، متن و ترتیب دستورجلسه‌ها، متن/نوع/ترتیب مصوبات و شناسهٔ تسک یا گزارش متصل. تغییر پیشرفت یا محتوای زندهٔ تسک/گزارش مرتبط، نام و فایل امضای پروفایل کاربران، وضعیت مشاهده و زمان‌های چرخهٔ جلسه نسخهٔ مصوبات را عوض نمی‌کنند.

هر امضا یک snapshot از محتوای تأییدشده را نگه می‌دارد. داده‌های قبلی هیچ امضای فرضی نمی‌گیرند. جدول مستقل انتخاب شده تا حذف عضو از pivot، تاریخچهٔ امضای او را نابود نکند و امضای نسخه‌های پیشین بازنویسی نشود. snapshot و تاریخچهٔ خام در پاسخ API عمومی نمایش داده نمی‌شوند.

اگر اصلاحی توسط مسیر مدیریتی آینده یا migration در محتوای نهایی انجام شود، امضای متفاوت با محتوای جدید به‌صورت outdated مشخص می‌شود و امضای مجدد ردیف تازه می‌سازد. این قابلیت، مجوز ویرایش جلسهٔ completed ایجاد نمی‌کند.

سرویس امضا همان ردیف جلسه را در تراکنش قفل می‌کند و عضویت، وضعیت و نسخه را دوباره بررسی می‌کند. مسیرهای فعلی تغییر جلسه/مصوبات نیز همان قفل والد را دارند. unique دیتابیس روی meeting/user/content از ثبت تکراری جلوگیری می‌کند. روابط موردنیاز یک‌جا بارگذاری می‌شوند و تعداد query با تعداد حاضرین رشد نمی‌کند.

## Migration

پس از انتشار کد و پیش از سرویس‌دهی با آن:

```sh
php artisan migrate --force
```

Migration افزایشی: `2026_10_27_000000_create_meeting_signatures_table`؛ ایجاد جدول امضاها بدون تغییر دادهٔ جلسات یا کاربران. rollback این migration جدول امضا و سابقهٔ آن را حذف می‌کند؛ روی محیط دارای امضای واقعی بدون پشتیبان اجرا نشود.


نتیجهٔ نهایی MySQL: **۴۵ تست موفق، ۶۴۳ assertion**؛ همهٔ ۱۵ تست جدید امضا در این اجرا نیز موفق‌اند. تنها استثنا، تست قدیمی rollback گزارش‌ها با ناسازگاری شناخته‌شدهٔ FK/index است؛ همین تست در SQLite پاس شده است.

موارد پوشش: هویت و مجوز، حساب غیرفعال، مدیر غیرعضو، وضعیت‌های قبل از اتمام، منع جعل امضاکننده/زمان، idempotency، امضای مستقل اعضا، استقلال مشاهده و اتمام، محتوای قدیمی و امضای مجدد، بقای snapshot، بازتولید هش از JSON ذخیره‌شده در MySQL، بررسی مجدد زیر قفل، قفل ویرایش‌های completed، unique دیتابیس و تعداد ثابت query با افزایش حاضرین.

Pint و git diff --check پاس شده‌اند. نمونه‌های JSON با schema اعتبارسنجی و فهرست مسیرها با Laravel تطبیق داده شده‌اند. مسیرهای قرارداد داشبورد با نسخهٔ قبلی برابرند. تست‌های خودکار روی دیتابیس production اجرا نشدند. پس از انتشار، بررسی بدون ثبت امضای واقعی روی سرور انجام و موفق شد. این نتیجه به معنی اجرای کل تست‌های نامرتبط پروژه نیست.
